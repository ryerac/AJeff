# Building and releasing AJeff

A release build and a published release are different things:

- A **local release build** is disposable and can be produced at any time.
- A **GitHub Release** is an official snapshot associated with a version tag.

Creating a tag does not freeze `main`. Development can continue normally after
a release; the tag continues to identify the commit that was released.

## Build locally

From the repository root, run:

```powershell
dotnet publish .\JeffDock.App\JeffDock.App.csproj -p:PublishProfile=win-x64-single-file
```

The output is written to:

```text
JeffDock.App\bin\Release\net10.0-windows\win-x64\publish\AJeff.exe
```

This is a self-contained Windows x64 executable. It includes the .NET runtime
and the official plugins, so it does not require an installer or a separate
.NET installation.

Use local builds for testing and release preparation. They do not require a tag
and do not create anything on GitHub.

## Continuous integration

[The CI workflow](../.github/workflows/ci.yml) runs for pull requests and pushes
to `main`. It builds the application and diagnostic CLI, then runs the tests. A
successful CI run means the commit compiles and passes the automated tests; it
does not publish a release.

## Version numbers

Release tags use semantic versions with a leading `v`:

```text
v0.1.0-beta.1  First beta of 0.1.0
v0.1.0-beta.2  Second beta
v0.1.0-rc.1    First release candidate
v0.1.0         Final 0.1.0 release
v0.1.1         Patch release
v0.2.0         Feature release
```

Treat every pushed release tag as permanent. If a release needs a correction,
commit the correction and create a new version instead of moving or reusing the
old tag.

## Publish a GitHub Release

Before tagging, make sure the intended commit is committed, tested, and pushed
to `main`:

```powershell
git status
git push origin main
```

Create and push an annotated tag:

```powershell
git tag -a v0.1.0 -m "AJeff v0.1.0"
git push origin v0.1.0
```

[The Release workflow](../.github/workflows/release.yml) starts when a pushed
tag begins with `v`. It then:

1. Validates the tag format.
2. Runs the automated tests.
3. Builds `AJeff.exe` with the version embedded in it.
4. Generates `AJeff.exe.sha256`.
5. Creates the GitHub Release with generated notes and both files attached.

Do not also create the Release through GitHub's **Draft a new release** page.
That page creates the tag and Release together, which conflicts with the
workflow attempting to create the same Release.

Follow a release run under the repository's **Actions** tab. After it succeeds,
download the executable from the repository's **Releases** page. The source ZIP
and tarball generated by GitHub are source archives, not the Windows app.

## Verify a downloaded release

From the directory containing both downloaded files, run:

```powershell
$expected = (Get-Content .\AJeff.exe.sha256).Split()[0]
$actual = (Get-FileHash .\AJeff.exe -Algorithm SHA256).Hash
$actual.Equals($expected, [StringComparison]::OrdinalIgnoreCase)
```

The result should be `True`.

## Troubleshooting

### The workflow did not start

- Confirm the tag was pushed to GitHub, not only created locally:
  `git push origin <tag>`.
- Confirm the tagged commit contains `.github/workflows/release.yml`.
- Confirm the tag begins with `v`.

### Tag validation failed

Use a tag such as `v1.2.3` or `v1.2.3-beta.1`. A name such as `release-1` does
not match the required format.

### The Release already exists

The Release was probably created manually before the tag workflow finished.
Use the automated tag flow for future releases. Do not rerun the workflow until
the conflicting draft or Release has been resolved.

### A released build needs a fix

Commit the fix and publish a new version. For example, follow `v0.1.0` with
`v0.1.1`, or follow `v0.1.0-beta.1` with `v0.1.0-beta.2`.
